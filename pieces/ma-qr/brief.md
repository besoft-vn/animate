# Brief — "Mã QR chứa thông tin như thế nào?" (Vạn vật vận hành như thế nào, 28/11/2026)

**Idea (one line):** a QR code is not a picture and not a pointer to a database: it is TEXT written in squares — dark = 1, light = 0, 8 squares = one letter; three corner squares tell the phone where the code is and which way is up; the letters are laid in a two-column zigzag from the bottom-right corner upward; a mask flips some squares so no big blocks form; and most of the rest is Reed–Solomon error correction computed from the data, so even with ~30 % of the codewords destroyed the code still reads.
**Device:** the orange pixel critter (hero) with a phone, and ONE REAL QR CODE (`src/qrdata.js`: content "CHAO!", version 1 = 21×21, level H, mask 001 = rows where row % 2 == 0 are flipped). Everything we show about it is true of this exact code.
**The end is the start, changed:** hook: a poster QR that "looks like noise" → end: the same poster with a logo in the middle, the phone scans it and reads "CHAO!".

**Format:** F5 fixed-hero journey, morph-joined on the hero (hero at the SAME spot `HERO_PX` [30, 300] px in every scene), one hard cut (SLAM = 39.0 s) into "payoff" inside the pause after "ecc". **Style:** pixel (styles/pixel), ONE resolution `RES` 270×480 (4 screen px per pixel), palette PAL16 (`Q.*`), no camera. 9:16, 24 fps, 120 BPM, 51.75 s, Vietnamese VO (Tuan Khang, eleven_v3).

**Colour = one meaning (whole video):** `Q.orange` = hero ONLY · `Q.white` / `Q.ink` = QR modules (light 0 / dark 1) · `Q.yellow` = finder patterns (position) · `Q.sky` = data bits, the letters, the zigzag path · `Q.pink` = the mask · `Q.lime` = error-correction modules · `Q.red` = damage / covering · `Q.night`/`Q.slate`/`Q.grey` = world, phone, frames, minor notes.

## The real code (src/qrdata.js)
`QR_M` (final, masked), `QR_RAW` (before the mask), `QR_KIND(r, c)` ('finder' | 'sep' | 'timing' | 'format' | 'dark' | 'data'), `QR_ORDER` (the 208 data modules in placement order: column pairs from the RIGHT edge, first going UP from the bottom-right corner, then down, …, skipping column 6), `QR_IDX[r][c]` (index in that order or −1), `QR_CHAR_C` = the 8 modules of the letter 'C' = 01000011 in stream order ([14,20],[14,19],[13,20],[13,19],[12,20],[12,19],[11,20],[11,19]) — read from `QR_RAW`, `QR_ISDATA` (bits 0–71: mode, count, C H A O !, terminator, padding), `QR_ISECC` (bits 72–207 = 17 error-correction codewords), `QR_HIT` / `QR_ISHIT` (codewords 0–7 = 64 modules, the payoff damage: verified still decodes), `QR_LOGO` [7,7,7,7] (centre 7×7: verified still decodes), `QR_MASKF(r, c)` = row % 2 === 0.

## Before / after the mask (IMPORTANT for honesty)
hook shows the final code (`QR_M`). From **bit** to **zigzag** show `QR_RAW` (before the mask) with a small grey note `(chưa phủ mặt nạ)` (size 13, top-right, px ~ x 130..235, y 82) — so the 'C' bits 01000011 really are what's drawn. **mask** flips data modules on even rows (pink stripes) → the code becomes `QR_M` again (= the hook's look). ecc / payoff / end use `QR_M`.

## Claims + sources (research.md)
- Dark = 1, light = 0; byte mode = 8 bits per character (Thonky; ISO/IEC 18004 via Wikipedia).
- 3 finder patterns (7×7, 1:1:3:1:1) give position + orientation; reading from any direction (DENSO WAVE qrcode.com).
- Data placed in 2-module-wide columns from the bottom-right, zigzag up/down (Thonky "module placement").
- 8 mask patterns, the one with the lowest penalty is chosen; avoids large blocks and finder-like patterns (Thonky "data masking").
- Reed–Solomon EC levels L/M/Q/H ≈ 7/15/25/30 % of codewords (DENSO WAVE; Wikipedia).
- Our code: version 1-H, "CHAO!", 9 data + 17 EC codewords; destroying 8 codewords (64 modules) still decodes — checked with OpenCV.
